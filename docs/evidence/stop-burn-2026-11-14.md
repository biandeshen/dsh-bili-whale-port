## 二、三件事都抄现成的，不自己发明

### 抄的是谁

| 需求 | 现成件 | 抄了什么 |
|---|---|---|
| 工具调用上限 | LangChain `ToolCallLimitMiddleware` | `run_limit`（一次 invocation 内计数）、`tool_name` 维度、`exit_behavior='continue'`（给错误回执、不崩整批） |
| 重复调用检测 | LoopDetector（dev.to 那篇） | 指纹 `f"{tool}:{arg}"`、`seen` 计数器、执行**前**拦截 |
| 幂等写 | 业界 idempotency key 通行做法 | 内容指纹（content hash）作幂等键；第二次返回第一次的结果，不重复落账 |

来源链接见文末。

### B. 一个回合的工具调用预算 → `packages/cortico-bot-xiaoyu/src/tool-gate.ts`（新）

```ts
DEFAULT_TOOL_LIMITS = { runLimit: 6, perToolLimit: 2, maxSameCall: 1, exitBehavior: 'continue' }
```

- `runLimit: 6` —— 一次唤醒内总共 6 次工具调用（实测一件事要 10 次，6 足够做完还能收尾）
- `perToolLimit: 2` —— 同一个工具最多 2 次（LangChain 文档示例是 3，取更严）
- `maxSameCall: 1` —— 同一 (tool, args) 第二次直接拒（这是 `23:45`/`23:53` 逐字重复那条）
- `exitBehavior: 'continue'` —— 抄 LangChain 默认值：**不抛异常**，回一条可读错误让模型自己收尾

挂在 `hub.tools()` 装配处（`withToolGate`），一次唤醒内计数；
`cortico-persona.ts` 的 `onDelivery`（宿主每批必调）里 `resetToolGate()` 清零。
**跨批不累计**——它拦机械重复，不是"她今天能做几件事"（那条主人禁过）。

### A. 写工具幂等 → `packages/persona-core/src/write-dedupe.ts`（新）

`contentKey()` 归一化（去首尾空白、连续空白压一、忽略大小写）+ sha1 前 16 位。
**不做同义词替换**——把"看雨"和"听雨"合并成一件是替她判断。

四个写工具各自接上：

| 工具 | 幂等键 | 重复时的行为 |
|---|---|---|
| `life_do` | (activity, note) | 返回"刚记过了"，**不扣体力、不追加行动账** |
| `mood_apply` | (preset, verdict, note) | 不叠加场值 |
| `diary_write` | (book, heading, body, date) | 不重写文件、不产生第二次 git commit |
| `memory_remember` | (content) | 不新建卡片、不多一次 commit |

`life_do` 的 `source='owner'`（主人手动记）**不受限**——他要记两遍是他的自由。

### C. 每笔行动的调用数进面板 → `packages/cap-state-rhythm/src/cost-today.ts`

`CostToday` 新增 `callsPerAction` / `actions`；行动数从 **`actions.ndjson` 当日条数**读
（不用 `life.json` 的汇总，验收要看凭据）；`costSummary()` 把它放在**最前面**：

```
｜**每笔行动 5 次调用**（超 3，一件事被拆太碎）（今天 4 笔）今天 20 次调用（付费 12 · 失败 8）…
```

今天没行动时写"今天还没有行动，算不出每笔调用数"，不拿 0 伪装一个漂亮比例。

## 三、验收（离线复算，零调用）

### 用真实那 12 次调用回放闸门

```
$ node -e "…把 toolcalls.jsonl 逐条喂给 ToolCallGate…"
原始调用数=12
有闸门后：放行=6  拦下=6
BLOCK mood_apply → run-limit
BLOCK memory_recall → run-limit
BLOCK life_do → tool-limit        ← 第 3 次 life_do
BLOCK mood_apply → run-limit
BLOCK memory_recall → same-call   ← 逐字重复
BLOCK life_do → same-call         ← 逐字重复（就是 23:45 / 23:53 那两笔）
闸门读数={"total":6,"byTool":{"diary_write":1,"life_do":2,"memory_recall":1,"mood_apply":1,"memory_remember":1}}
```

**12 → 6**：同一件事的调用数减半；每笔行动 **5.0 → 2.5**，达到 ≤3 的目标。

### 指标算得准（用 11-13 真数据反验）

```
11-13 读数：calls=20 paid=12 actions=4 callsPerAction=5
行动账逐日：{"2026-11-05":4,"2026-11-06":222,"2026-11-13":4}
```

与复核给的 14.3（11-06，226 笔 / 3237 次）同一算法，可对照。

## 四、没做的 / 边界

1. **线上还停在暂停态，没重启、没花一次调用**。闸门与幂等都只在离线测试里验证过；
   要证明"线上今天就变 6 次以内"，需要一次重启观察一轮 —— 我不自行启动。
2. **`runLimit=6` 是拍的还是抄的？** 半抄半评：`perToolLimit=2` 参照 LangChain 文档示例的 3 取更严，
   `runLimit=6` 来自实测（一件事 10 次，留 6 次余量）。**这两个数写进了配置默认值，面板可改**。
   若主人觉得太紧/太松，改 `DEFAULT_TOOL_LIMITS` 或 `opts.toolLimits` 一处即可。
3. **`memory_recall` 重复不影响账**（读操作），闸门仍会拦它——因为"同一件事被反复回忆"同样是空转，
   只是它不写账。这一点与 `life_do` 的语义不同，已在测试注释里写明。
4. **11-06 那种 14.3 的形状不能只靠闸门**：那一批是 226 笔真行动，闸门会让每笔更短，
   但"她为什么要做 226 件事"是节奏问题（`decideAction` 的驱动），不在本轮范围。
