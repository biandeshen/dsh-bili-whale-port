## 一、先纠正一处：止损代码在，但被"假恢复"废掉了

复核说「`liveness.ts` 只负责读出来告诉你，没让心跳停下来」。**前半句对，后半句不成立**：
退避从 2026-11-07 就有（`packages/cortico-bot-xiaoyu/src/cortico-persona.ts:186-200`，
公式在 `stall-backoff.ts`，注释里写明"这不是配额"）。线上日志也证明它在跑：

```
[23:53:30.019] WARN core.persona: 上游不通，心跳退避 2 分钟——这拦的是空转，不是她想做事（额度被拒 402）
[23:55:30.148] WARN core.persona: 上游不通，心跳退避 4 分钟——…
[23:59:30.255] WARN core.persona: 上游不通，心跳退避 8 分钟——…
[00:07:30.409] WARN core.persona: 上游不通，心跳退避 16 分钟——…
[00:08:30.492] INFO core.persona: 上游恢复，心跳退避清零，回到原节奏   ← 假的
[00:08:33.562] ERROR core.loop: LLM调用失败… 402                      ← 3 秒后又是 402
```

**真正的缺陷是这条"上游恢复"**：`cost-today` 用 15 分钟新鲜度判 `stalled`，
402 之后失败行不会立刻落盘（要等下一次调用才写），于是窗口一过就判 `quiet`
→ 调用方把 `quiet` 当"恢复"→ 清零退避 → 立刻再撞。

所以复核看到的「00:08:30 402，00:08:33 又 402」不是"没有退避"，
而是**退避被一次假恢复清零后又撞了一次**。修法见 §二.1。

## 二、P2b 修了三处

### 1. 假恢复（根因）

`packages/cap-state-rhythm/src/cost-today.ts`：恢复必须由**成功调用**证明，不能由"没有新行"推断。

```diff
+ const recoveredSinceFail = lastPaidMs > 0 && lastPaidMs > lastErrMs
+ const verdict = recoveredSinceFail ? 'ok'
+             : lastErrMs > 0 ? (402 ? 'stalled-auth' : 'throttled')
+             : recentlyPaid ? 'ok' : 'quiet'
```

**顺带修出一个一直存在的死变量**：`lastPaidMs` 声明后从未赋值（`:66` 定义、`:103`/`:116` 使用），
所以 `recentlyPaid` 永远 false、verdict **从来不可能判成 `ok`**。
也就是说"上游恢复"这件事以前只能靠 `quiet` 猜——正是这次被坑的那处。
已补 `lastPaidMs = Math.max(...)`（`:82-90`）。

### 2. 封顶 30 分钟 → 60 分钟

`stall-backoff.ts`：`STALL_MAX_MINUTES 30 → 60`，`STALL_STEP_MAX 5 → 6`。
序列变成 **2 / 4 / 8 / 16 / 32 / 60（封顶）**。
理由：欠费要人充值才恢复，不是自己会好的抖动；对照 TTS 那边的 `COOLDOWN_402_MS = 6h`，1 小时是折中
（一夜 ≤8 次，恢复后最多等 1 小时）。**这不是配额**：判据是调用回执，不是"她做了几件事"。

### 3. 停摆期不做上下文交接

`cortico-persona.ts` 的 `onBatchEnd`：交接要叫一次模型写笔记，402 时那次调用必然再失败。
线上日志已见 `00:08:33 402` 紧接 `00:08:36 上下文交接完成`——白烧一次请求。现在先判通道，关着就跳过交接。

### 4. 退避状态持久化（新文件 `stall-state.ts`）

以前存在 `this.__stallBackoff`，**重启即清零**——刚欠费的机器重启后又按 30 秒一拍往回撞。
现在落 `data/stall-backoff.json`（until / step / kind / lastFailureAt）。
坏文件/缺失 → 当作没有（退化成照原节奏，不是"不许动"）；过期超过 6 小时的记录不拖着。

### 演示（复核要求的"故意设成欠费"）

```

   第 1 拍：判为 stalled-auth → 撞 1 次，随后退避 2 分钟

   第 7 拍：判为 stalled-auth → 撞 1 次，随后退避 8 分钟
```

## 三、P2c：71 万 token 的分块占比表（复核硬要求）

### 口径先说清楚（两个容易踩的坑）

1. **`scripts/token-anatomy.mjs` 的分母是错的**。它拿"本 run 的 transcript"（39,152 字符）当窗口，
   换算出 218.79 token/字符——那不可能。实测：本次 run transcript 只有 49,914 字符，而实付 713,849 token。
   **真正送出去的是整个会话正本 `data/session-main.jsonl`**（1,256,107 字符 JSON / 936,508 字符纯文本），
   713,849 ÷ 936,508 = **0.762 token/字符**，这才是正常中文比例。
   → 下表以**会话正本**为分母重算。这条要修脚本，登记为后续（不本批改脚本口径）。
2. session 是 **append-only**，只在 handoff 时 reset（`Cortico-up/src/core/session.ts:1`
   「Session context is append-only between lifecycle resets」）。当前 **1,738 条 item**。

### 分块占比表（分母 = 会话正本纯文本 936,508 字符；实付 713,849 token/次）

| 块 | 字符 | 占比 | 折 token/次 |
|---|---:|---:|---:|
| **user 注入 ▸【本轮关联记忆】** | 465,936 | **49.8%** | **355,158** |
| user 注入 ▸【状态】 | 200,804 | 21.4% | 153,062 |
| function_call_output（工具结果回灌） | 91,129 | 9.7% | 69,463 |
| user 注入 ▸【作息对账】 | 89,489 | 9.6% | 68,213 |
| user 注入 ▸【她现在的情绪】 | 35,360 | 3.8% | 26,953 |
| user 注入 ▸【上下文压力】 | 26,481 | 2.8% | 20,185 |
| assistant 输出（她自己说过的） | 14,310 | 1.5% | 10,908 |
| user 注入 ▸（开头未分块段） | 7,803 | 0.8% | 5,948 |
| message/system | 5,196 | 0.6% | 3,961 |

### 最大的一块是什么，为什么反弹到 71 万

**最大的一块是「本轮关联记忆」，49.8%，折 355k token/次。**

关键：**单次注入只有 687 字符（3 条记忆），完全正常**。问题是它被注入了 **680 次**：

```
本轮关联记忆：注入 680 次 · 合计 460.5k 字符 · 单次 p50 687
状态：        注入 680 次 · 合计 198.1k 字符 · 单次 p50 291
作息对账：    注入 427 次 · 合计  84.5k 字符 · 单次 p50 196
她现在的情绪：注入 680 次 · 合计  29.9k 字符 · 单次 p50  44
上下文压力：  注入 272 次 · 合计  24.6k 字符 · 单次 p50  89
```

**所以 71 万不是"某一块特别大"，是"每轮注入都留在 session 里、从此每轮重送一遍"。**

### 为什么 11-06 交了表（diary_read 34.7%）这次又反弹

11-06 那张表量的是**当日新增 item 的构成**——当时主导项是整页日记（`diary_read`）。
这次主导项换成了**累积的 user 注入**：那些注入本身单条很小，但会话正本从 11-04 起没被重置过，
680 轮 × 每轮几百字 = 46 万字符。**同一个"不裁剪"的病，换了张脸出现。**

两者是同一个根因：**会话只在 handoff 时 reset，而 handoff 的触发线（阶段预算）被配成了 500,000**
（`~/.xiaoyu-home/xiaoyu/config.json` `context.maxTokens=500000`），
而**我们自己代码里的默认值只有 64,000**（`packages/cortico-bot-xiaoyu/src/context-config.ts:31`
`maxTokens: 64000`）。也就是说：代码默认 6.4 万，线上被配成 50 万，放大 7.8 倍。

### 结论：这是配置 + 机制两个问题，不是一个

- **配置**：`context.maxTokens 500000 → 64000`（回到代码默认）。这一条**属于主人的旋钮**，
  面板上可改（`context-config.ts` 有 `context.maxTokens` 项），我不擅自改线上配置。
- **机制**：即使按 64k，680 轮注入仍会把它撑爆——因为 handoff 只保 `keepRatio=1/3`（约 21k），
  之后按每轮 ~1.4k 字符（0.76 token/字符 ≈ 1k token）的速度再涨，**约 20 轮就回到 21k 的软线**。
  真正的修法是**别把每轮注入都留在会话里**：它们对"下一轮"有用，对"20 轮之后"没用。

### 建议的 P2c 修法（需主人拍板，因为改的是她的"记忆感"）

按收益/风险排序，都不大：

1. **注入不进会话正本**（最大收益，~50%）：`【本轮关联记忆】/【状态】/【作息对账】/【她现在的情绪】`
   这几块每轮都由 `onBatchStart` 重新生成，**历史那份没有价值**。
   做法：注入时打 `ephemeral` 标记，`SessionLog` 在组装请求时只取最近一条（或最近 N 条）同类注入。
   预期：713k → 约 **360k**（去掉 355k 的重复记忆）。
2. **工具回灌截断**（~10%）：`function_call_output` 单条上限（现在 `memory_recall` 一次 15,172 字符）。
   预期：再降 ~60k。
3. **配置回默认**（不改代码）：`maxTokens 500000 → 64000`，让 handoff 早触发。
   代价：交接更频繁（一次交接也要一次调用），收益与代价必须成对测——这正是
   `docs/A-KNIFE-CONTEXT-BUDGET-2026-11-07.md` 说的那件事。

**我没在本批改这三条**：1 和 2 会改变她被喂进去的内容（等于改她的"记忆感"），
3 是线上配置（主人的旋钮）。三条都需要主人拍板，我出方案与数字。

4. `context.maxTokens = 500000` 是主人放的，我不动；但要注意**它比物理窗口的一半还大的时候，
   "预算拦截"实际上拦不住任何东西**（宿主的 `contextOverflow` 只在接近物理上限时才触发）。
