# D-34 看门狗跨日不收尾 → 每天的 state.end 都缺 —— 证据（2026-10-29）

> 发现：09:26 复查 10-28 日报时，`state.end.json` 为 MISSING；看门狗 04:01 直接给新一天打了第 1 个 tick，没有给前一天收尾。
> 处置：修**跨日收尾**；10-28 不回填，如实留在日报里。

## 1. 事实

- `day-watchdog.mjs` 的 `once()` 只 `seed + tick`，全仓只有 `day-snapshot.mjs --end` 会写 `state.end.json`，但没人调用。
- 日志证据（`control/day-watchdog.log:65-66`）：

```
[2026-10-28T19:56:37.623Z] tick 2026-10-28 count=49
[2026-10-28T20:01:37.657Z] tick 2026-10-29 count=1     ← 直接跨日，10-28 没有 end
```

- 影响：`day-report` 对每个过去日都会报 `state.end.json MISSING`；观测期无法证明“这一天正常收口”。
- 注意：这不是机器睡眠导致，看门狗当时在跑（每 5 分钟一条）。

## 2. 修法（只向前生效）

| 文件 | 改动 |
|---|---|
| `scripts/day-snapshot.mjs` | 新增 `closeFromLastTick(day)`：用该日**自己最后一条 tick** 的快照写 `state.end`，带 `derivedFromLastTick` 与 `endedAt`；已有 end 不覆盖；没有 tick 不写；最后 tick 超过 2h（睡过日界）不写 |
| `scripts/day-watchdog.mjs` | 进程亲历日界时调用 `closeDay(lastDay)`；**启动时不回补历史**（缺失就如实留着） |
| `tests/day-close.test.mjs` | 4 例：收尾只用最后一条 tick（故意把当前 fields 写成 0.99，end 仍应是 0.62）；已有 end 不覆盖；无 tick 不写；睡过日界不收尾；C2 窗口允许陈旧 tick 但写 `derivedReason` |

为什么不用当前状态写 end：04:00 之后 `life.json` 已滚到新一天，`collect(prevDay, now)` 会把新一天的 actionsToday/fields 写进昨天，属于回填 + 串日。用最后一条 tick 是“当天最后一次真实观测”。

## 3. 验证

```
node --test tests/day-close.test.mjs
# tests 2 / pass 2 / fail 0

重启看门狗（pid 169964）
[2026-10-29T01:27:44.162Z] start pid=169964 interval=300000ms
[2026-10-29T01:27:44.210Z] tick 2026-10-29 count=67
```

10-29 的 `state.end` 将在下一次日界（10-30 04:00）由新逻辑写入；能否写入取决于进程是否亲历日界，机器睡眠跨过 04:00 仍会缺——那时按 `late/missed` 记录，不补。

## 4. 10-28 现状（不回填）

```
node scripts/day-report.mjs --date 2026-10-28
MISSING  state.end.json
MISSING  draft.diaryHash  （旧草稿或未记录）

```

10-28 仍会判不通过 G3b；这是真实损失，不用“补一个 end”来掩盖。
