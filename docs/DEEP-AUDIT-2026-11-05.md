## 1. 活故障取证（7 条，逐条可复核）

### 1.1 心跳无条件唤醒模型 【根因，P0】

`packages/cortico-bot-xiaoyu/src/cortico-persona.ts:125-127`：

```ts
if (typeof core?.injectDeferred === 'function') core.injectDeferred('tick', make)
else core?.injectInternal?.(make())
```

`make()` 里调 `rhythm.lifeTick()` 拿到 `tick.shouldAct`，`rhythmLine(tick)` 也**已经按
`shouldAct=false` 写了"这一拍就待着"的话**（`:155-163`）——
**但不管 shouldAct 是 true 还是 false，都照样注入、照样唤醒模型。**

后果：`decideAction` 的概率门（`persona-core/src/rhythm.ts:108`，`rng() >= urge * CHECK_PROB`，
CHECK_PROB=0.05）本来是"要不要叫醒她"的闸，现在变成了"叫醒她，然后告诉她别动"。
她每 5 分钟被叫醒一次，花一次模型调用，回一句"待着，不动"——**66 次**。

> `rhythm.ts:46` 的注释自己写着："保守的兜底仍是'一分钟最多被检查一次'× CHECK_PROB，不会狂刷"。
> **设计意图是概率门决定是否唤醒，实现成了唤醒后再播报概率门的结果。**

### 1.2 空拍退避永久失效 【根因，P0】

`life-heartbeat.ts:95` 有退避：`base * Math.min(2 ** idleTicks, 8)`（最长 8× = 40 分钟）。
`:119-120` 的推进条件：`if (lastActivity > lastFire) idleTicks = 0`。

而 `cortico-persona.ts:301` 在 `onDelivery` **第一行**无条件调 `noteActivity()`：

```ts
// 有外部事件到达 = 她被人叫过：心跳的空拍退避清零
this.heartbeat?.noteActivity()
```

注释的假设是"有外部事件到达"，但**心跳自己注入的 tick 也是走投递进来的**——
于是每拍都把 `lastActivity` 推到 `lastFire` 之后，`idleTicks` 永远归零。

实测印证：会话里连续两条 tick 都写"已安静 5 分钟"（#243、#246），**退避一次都没生效过**。

### 1.3 她模仿合成帧，整轮被丢弃 【P0】

宿主 `Cortico-up/src/core/loop.ts:884-891` 的 `dropReservedCalls`：
模型若吐出保留帧名（`external_event_frame`）的 function_call，**丢弃**，
注释写明"删除后没有工具调用的响应按自然结束处理"。

日志实测 **12 次** `模型仿造保留帧调用,已丢弃`。

为什么她会模仿：`appendEventFrame`（`loop.ts:868-878`）把外部事件写成
**assistant 角色的 function_call + function_call_output** 存进会话。
她在控制台页面上看到的就是这个样子（我实测截到：`ASSISTANT #12 / tool_name external_event_frame / 合成`）。
**上下文在教她伪造事件帧。**

对你的直接后果：#247 那一轮她只说了
"主人问「怎么不动」——得回答。…让我先看看池子里有没有可以动的东西。"
——**这是自言自语，不是回答**，而且后面没有正文跟上。你看到的就是"不回消息"。

### 1.4 同一次请求里她的体力有两个值 【P1】

控制台实测（同一次会话、同一屏）：

- SYSTEM 段：`【状态】体力38 刺激80 …`、`最近发生：她想去做点什么（energy 0.43→0.38）`
- 同批 user 注入：`【状态】体力88 刺激80 …`

**38 与 88 同时在场。** 两个注入路径不同源：`systemSegments` 是会话级、
`onDelivery` 注入是每事件级，长会话里前者会陈旧。她拿到自相矛盾的身体状态。

### 1.5 召回僵化：连续多轮想起同样三条 【P1】

#242–#248 每一轮的【本轮关联记忆】都是同样三条：

```
主人没让发那条草稿（…8D 雨声已经不是今天的事了）（dyn-20261029-8e3377）
主人没让发那条草稿（…**1** 这种星号在 B 站动态里不渲染）（dyn-20261028-051a57）
主人没让发那条草稿（旧的 dry-run：当天的热评稿已过时效）（dyn-20261027-5a8d88）
```

三条都在**核心常驻**里（控制台 SYSTEM 段实测 8 条核心常驻，其中 3 条是这个主题）。
她的注意力被钉在十天前的三次拒稿上，**每一轮都重新想起一遍**。

打分公式在 `persona-core/src/retrieval.ts:150`：
`0.40*关键词 + 0.30*鲜活度 + 0.15*情绪 + 0.15*新近`——
**没有多样性项**（同一主题重复命中不衰减），也没有"已经在上下文里的就不再召回"。

### 1.6 验收脚本的残留进了她的真实记忆 【P1】

SYSTEM 段"最近发生"实测：

**我的验收脚本污染了她的长期记忆**，而且污染进了"每一轮都记得"的核心常驻层。

## 3. 做深：外部机制 → 我们的差距 → 怎么做

这一节每条都是**读了原文取到的具体机制**，不是标题党。

### 3.1 检索打分：我们缺两项，而且缺的那两项正好是 LongMemEval 里掉分最狠的

**Generative Agents（Park et al. 2023）原文机制**：
- 记忆流记录字段：自然语言描述 + 创建时间戳 + **最近访问时间戳**
- 打分 `score = α_r·recency + α_i·importance + α_a·relevance`，**三个 α 都 = 1**
- recency：**指数衰减 0.995**（按游戏小时，自上次访问起算）
- importance：**LLM 打 1–10 的 poignancy 分**（写入时打一次）
- relevance：embedding 余弦相似度

**LongMemEval（500 题 / 115k token）五项能力**：IE 信息抽取 · MR 跨会话推理 ·
**KU 知识更新** · **TR 时间推理** · **ABS 弃答**。商用系统整体掉 **30–64%**。
论文给的有效手段：**时间感知的查询扩展**改善 TR，**问题分解**改善 MR。

**Zep/Graphiti（arXiv 2501.13956）**：**双时间轴**，每条事实带 `valid_at`/`invalid_at`，
**新事实作废旧边**而不是并存；图分三层 episodes → entities → communities。
实测 DMR 94.8%（MemGPT 93.4%）；LongMemEval 上准确率 **+18.5%**、延迟 **−90%**。

**我们的位置**（`retrieval.ts:150`）：`0.40*关键词 + 0.30*鲜活度 + 0.15*情绪 + 0.15*新近`

| 能力 | 我们 | 差距 |
|---|---|---|
| IE | ✅ 关键词命中 | 只有关键词，同义不同词就想不起来 |
| MR 跨会话推理 | ❌ 无 | 没有反思层（§3.2） |
| **KU 知识更新** | ❌ 无 | 没有 valid_at/invalidatedBy，相反的两条并存 |
| **TR 时间推理** | ⚠️ 弱 | 有新近因子，但**查询不带时间**（"上周那条"问不出来） |
| **ABS 弃答** | ⚠️ 半个 | `dreamDigest` 会说"想不太清了"，但那是叙事，**不是检索时的弃答行为** |
| **多样性** | ❌ 无 | §1.5 实测：同一主题三条连续多轮重复召回，没有去重/衰减 |

**怎么做（按性价比排序）**：
1. **加多样性惩罚**（最小改动、直接治 §1.5）：同一主题/同一 dyn-id 前缀在本轮已命中过就降权；
   已在上下文里的不再召回。
2. **加 importance 分**：写入时让模型打 1–10（Generative Agents 的做法），
   替代现在纯靠"鲜活度"。核心常驻准入也用这个分。
3. **加时间有效期**：`validAt` / `invalidatedBy`，冲突时作废旧条（照 Zep 语义，不用上图数据库）。
4. **弃答**：召回分数全低于阈值时，明确注入"这件事她记不清了"，而不是硬塞最接近的三条。
5. **不要上向量检索**：`retrieval.ts:4` 的论证成立（不可复现、要外部依赖、解释不了为什么想起这条）。
   要补语义只能做**混合 + 可解释**（向量当平局裁判，命中理由写进因果账）。

### 3.2 反思与睡眠计算：我们的"做梦"是拼字符串，别人是真跑推理

**Letta sleep-time compute（arXiv 2504.13171）原文机制**：
- 空闲时对已有上下文离线"重想"，产出**重新表示的上下文 c′**
- 实现是 `rethink_memory` 调用，**最多 10 次**，提示词形如 "Make as many inferences…"
- 实测：**测试期 token 降约 5×，准确率最高 +18%**

**Generative Agents 的 reflection 原文机制**：
- 触发条件：**最近事件的重要性分累计 > 150**
- 频率：**每天 2–3 次**
- 做法：先让模型就最近事件**提 3 个高层问题**，再对每个问题检索证据、
  生成**带证据引用的洞察**，洞察本身**写回记忆流**（叶子是观察，向上是反思树）
- 消融实验：observation / planning / reflection 三者对可信度**都是关键贡献**

**我们的位置**：`cap-memory/src/card-store.ts:404-412` 的 `dreamDigest()` 全文就是拼字符串：

```ts
return `夜里结算记忆：${items}${more} 想不太清了，只剩个轮廓。原文都还在（git 兜底）…`
```

**零模型参与**。全仓 `grep reflection|反思|归纳` → **零命中**。

**更打脸的是：我们自己已经有活动库，但是死代码。**
`persona-core/src/life-activities.ts` 定义了 **7 类活动**
（rest / explore / create / social / **reflect** / exercise / consume），
每类多条中文模板（"窝在椅子上，听窗外的声音发一会儿呆"…），
按场值打分选 k 条（`pickActivities`）。

但实测：`pickActivities` 的引用只有 `persona-core/src/index.ts:12` 的再导出 + 测试文件，
**生产代码零调用**。而 `decideAction` 的 `ActionKind` 只有 **3 种**：
`'explore' | 'connect' | 'restless'`（`rhythm.ts:29`）。

> **她的行动词汇表只有三个词，而我们已经写好的七类活动库躺在那儿没人调。**
> 这是"做深"里性价比最高的一条：不用写新逻辑，把已有资产接上。

**怎么做**：
1. **先接死代码**：`decideStage` 决定要动之后，用 `pickActivities` 按场值选出**这一轮做什么**
   （7 类而不是 3 类），把 label 写进注入文本。她会立刻"活得细"起来。
2. **反思按 Generative Agents 的阈值触发**：不是每夜固定跑，而是
   **当天事件重要性累计过阈值才跑**（省钱，且反思有意义时才发生）。
3. **反思产物写回记忆卡**（新的一层或标 `kind: reflection`），
   并在日记面板显示——这样你能看见她"想明白了什么"。
4. **sleep-time compute 版本**：夜里把当天因果账 + 日记 + 收件箱喂给模型，
   产出三样：① 反思条目 ② 明日倾向 ③ 对主人可能问的事的预答。
   **这条要花钱，需要主人点头**；不点头就只做 1–3（离线归纳，用已有产物）。

### 3.3 上下文工程：我们自己就在制造 context rot

**实测数据（Stanford lost-in-the-middle，转引自 Redis 2025-12 综述）**：
20 篇文档（约 4000 token）时，信息在**位置 1 或 20 → 准确率 70–75%**；
**在中间 → 55–60%**。**掉 15–20 个百分点，只因为位置，与内容质量无关。**
另一条反直觉结论：**长上下文任务里 CoT 反而会降分**（往已经吃力的窗口里塞更多 token）。

**我们的位置**：控制台实测"下次提交 **54.9k tok**"、会话 248 条、
每条 user 消息都带**同一份约 500 token 的状态块**（情绪 + 状态 + 最近发生 + 记得 + 本轮关联记忆）。

111 条心跳 × 500 token ≈ **5.5 万 token 的重复状态块**。你的 9 条真消息埋在中间——
**正好是准确率最低的位置**。

**怎么做**：
1. **状态块去重**：同一拍内状态没变就不重复注入；变了只注入 diff（"体力 88→38"）。
2. **真消息置顶/置尾**：主人的话必须落在高注意力位置，不能被 111 条自我对话推到中间。
3. **心跳不唤醒模型**（§1.1）——这一条同时解决噪声、成本、位置三个问题。
4. **固定上下文规模 + 外部检索**：Redis/业界共识是别指望把全窗口塞满，
   保持窗口固定、按需检索。我们的 `context.maxTokens=200000 / keepRatio=0.4` 是交接策略，
   不是"塞多少"的策略。

### 3.4 人格漂移：有现成的便宜办法，而且和我们已有的东西对得上

**ContextEcho（arXiv 2605.24279）原文机制**：
- 漂移定义：`Δ(t, M) = mean(filler score) − mean(claude score)`
- **25 个探针，分 5 类，跑了 23 个模型**
- 结论：漂移**跨厂商普遍**、**很早就开始**、**compaction 之后仍然存在**
- 缓解：**80 token 的单发锚点**就能恢复语域，**不需要重训**

**我们的位置**：`check-live-drift.mjs` 查代码/配置漂移，`cortico-health` 查身份锚（账号名在不在前缀里）。
**行为漂移零指标**。

**怎么做（不花钱、不动观测窗基线）**：
1. **80 token 锚点**这条直接印证了我们的路线——身份锚是对的，只是现在只在前缀里静态存在。
   可以做成交接后**重新注入**（ContextEcho 说 compaction 后漂移仍在，正好对应我们的 keepRatio 交接）。
2. **25 探针 / 5 类**的形状可以照抄：写一套她的探针（自称、称呼主人、拒绝越界、
   审美口径、对 B 站的态度），离线跑她的历史产物打分，**不新调模型**。
3. 三个指标先立基线：身份锚命中率 / 口吻一致性（句长、语气词分布）/ 越界拒绝率。

### 3.5 成本：我们缓存命中 90%，但一分钱都算不出来

**实测（线上 `usage.jsonl`，1044 行）**：
90 次调用 · prompt 260.9 万 token · completion 1423 · **缓存命中 235.5 万（90%）** · **cost 0**

**外部基准**：
- Prompt caching 跨厂商实测：**省 41–80% 成本，TTFT 快 13–31%**（arXiv 2601.06007）
  → 我们 90% 命中率说明**这块已经做得很好**，别去动它（§3.3 的状态块去重不要打破前缀稳定性）
- OTel GenAI 语义约定字段：`gen_ai.request.model`、`gen_ai.usage.input_tokens`、
  `gen_ai.usage.output_tokens`、`gen_ai.response.finish_reasons`、`gen_ai.system_instructions`、
  `gen_ai.input.messages`、`gen_ai.output.messages`；
  指标 `gen_ai.client.operation.duration`、`gen_ai.client.token.usage`。
  **成本不在标准里**——要自己按价格表算
- LiteLLM / agentgateway：**硬预算 fail-closed**、每 key 上限、RPM/TPM 三重限流
- RouteLLM：成本感知路由，报告可省 85%

**怎么做**：
1. **补 MiMo 价格表** → 立刻有钱数（最小改动、最大可见性）
2. **未计价必须明写**，不能显示 0 冒充免费
3. **日花费上限 fail-closed** + 面板显示"今天花了多少 / 上限多少"
4. **按任务路由**：看片摘要走 flash、日记/反思走 pro（MiMo 有两档）
5. **别自造观测栈**：要 tracing 就接 OTel GenAI 约定或自托管 Langfuse/Phoenix

### 3.6 内驱力：我们的场值设计其实是对的，缺的是"自己产生目标"

**外部**：内稳态内驱力架构（Cat Intelligence / 知乎 2026）、
Frontiers in AI 2024《Intrinsic motivation in cognitive architecture》、
DeepMind《Is Curiosity All You Need?》、
Continuity Core 的 MRA（用"认知压力最小化"产生自主好奇）。

**我们的位置**：`persona-core/src/decay.ts` 的 `BASELINES` + 向基线衰减 = **标准内稳态**；
六个场值里就有 `curiosity`；`applyHardCouplings` 有正负耦合（被陪着能托起来）。
**这套设计和文献是对得上的，不用改。**

缺的是：
- **目标是自己生成的吗？** 不是。`decideAction` 从 3 个固定 kind 里挑一个。
- **活动库死代码**（§3.2）：7 类活动没人调。
- **认知压力**这种"我不知道所以想去查"的驱动没有。

**怎么做**：先接 `pickActivities`（7 类），再考虑加一类"她注意到自己不知道的事 → 生成一个查询目标"。

### 12.2 「连接与凭据」面板 + 写侧凭据的两个真 bug（B13b-2）

粘贴 cookie → 先问 B 站"这是谁" → **验过了才落盘**；解绑是显式动作；凭据值永不回显（体检只给有无 + sha1 前 6 位指纹）。

顺手挖出两个一直在坏的东西：

1. **写侧是第二份凭据解析**：`bili-write.ts` 只认 JSON，而部署家的 `.env` 是 `NAME=value`。
   同一个文件喂读写两条路，写侧读出来是三个空串——她带着空 cookie 去发评论，
   平台回 -101/412，页面看起来像"被风控"而不是"没登录"（本仓 2026-11-05 刚为这个烧过一轮）。
   现在两侧共用 `parseCredentials` 一份实现，并额外认浏览器 DevTools 那种 `a=1; SESSDATA=…` 的 Cookie 头。
2. **世界转接头把凭据取成启动快照，还把 `bili_jct`/`buvid3` 写死成空串**：
   `writeContext: { cred: { sessdata: safeSecret('BILI_SESSDATA'), bili_jct: '', buvid3: '' } }`——
   意味着 CSRF 令牌从来没送到写侧，而且换完 cookie 不重启就还是旧的。
   现在改成 `liveCredentials(file)`（每次取现读，进程环境变量优先，与宿主 `secretReader` 同一条优先级），
   转接头不再塞快照。线上体检直接印证：`SESSDATA 已填 / bili_jct 已填 / buvid3 已填`。

另外两条写下来的教训：

- `writeConnectionRecord` 原来是**空 catch**，把一句 `ReferenceError: fs is not defined` 静默吞掉了——

### 12.5 「回滚到这里」落地（B13b-4）：形状要真形状，别拿脑补的假数据喂测试

设计走查 story-7 说的是「版本历史每条带回滚 + 确认」。这一片把入口补上时撞上一件
**只有真浏览器能照出来**的事，链路很短，值得原样记下来。

**后端早就有**：`<workspace>/.git` 里 `checkpoint0` 是 annotated tag，
`WorkspaceGit.checkoutTag()` 走 `reset --hard <tag>` + `clean -fd`（在当前分支上移动指针，
不是 detached HEAD），面板方法 `rollback` 也一直在、还要求显式 `confirm: true`。
缺的是**页面上那颗键**——描述里承诺"可回退"，页面上只有"看改动"。

**写完离线测试全绿，线上却是 `undefined`。** 真浏览器点验时，存档点那一行渲染成：

```
存档点与回滚
1 个存档点。回滚会丢掉它之后的记忆与日记改动，并把未跟踪的文件一并清掉。
undefined                 ← 这里应该是存档点名
⏮ 回滚到这里
```

根因在**形状对不上**，不在渲染：

| 位置 | 形状 |
| --- | --- |
| `GitStatus.tags`（后端真返回） | `string[]`（只有名字） |
| 面板按什么读（我写的） | `{ name, message, hash, date }[]` |

`status.tags` 里每个元素是字符串，于是 `t.name` 是 `undefined`、`t.date` 也是 `undefined`。
更要命的是按钮会发 `{ name: undefined, confirm: true }` 给后端——**功能是坏的**，
只是坏得"像报错"（后端会回「没有这个 checkpoint:」）而不是"像没事"。

**为什么离线测试没照出来**：DOM 测试用的是我手写的 fixture——
我按自己以为的形状写了对象，于是断言全绿。**fixture 是我自己编的，测试就只验证了
我自己编的东西**。TypeScript 不拦（Node 24 直接剥类型，类型只是文档），
所以只有「后端真 git + 真浏览器」这条链能照出来。

修法（两处都要动）：

- `GitStatus.tags: string[]` → `GitStatus.checkpoints: CheckpointInfo[]`
  （`name/message/hash/date`，`status()` 里直接给 `listTags()` 的结果）；
  `checkpoint` / `rollback` 两个 POST 的回包也统一成 `checkpoints`。
- 面板读 `res.status?.checkpoints`；**名字拿不到就不给那颗键**（宁缺毋滥：
  发一个 `undefined` 的存档点名，只会让人看到一句看不懂的报错）。

**钉住形状的断言放在真 git 那条链上**（`packages/cap-memory/tests/git-history.test.mjs`，
真建仓、真打 tag、真回滚）：断言 `checkpoints[0].name/message/hash/date` 都在、
`date` 能 `Date.parse`、`status.tags` 已退场、`rollback` 收到空名字要回「没选到存档点」。
并做了**变异验证**：把后端退回"只给名字"，这条断言立刻变红（`带说明` 失败），改回来又绿——
不是"写完看着对"，是"证明这条断言真能变红"。

DOM 测试同步补了两条：拿到旧形状（只有名字）时**不许长出回滚键**、
存档点缺名字时**只亮说明不给键**；另外页面文本里出现 `undefined` 一律判红。

**真浏览器点验（线上 7799，全程只点取消）**：

- 存档点行现在显示真名：`checkpoint0 · 2026/11/4 00:59:59 · 出厂/重置后的干净状态(init 自动)`，

#### 二、看片偏好规则命中统计

- 新增 `<dataDir>/pref-hits.json`：`dislike{词→条数}` / `tooShort` / `scanned` / `updatedAt` / 最近 8 条命中样本。
- 计数只在**真的看过一条内容并判定它命中**时 +1，不在"保存词表"时 +1——
  否则数字越大越好看，越好看越不真。
- 样本（被拦下的标题）留着，是为了**核对是不是误伤**：宽词一旦误伤，主人能当场看见是哪条。
- 面板 `preferences` 加两块：`hits`（GET，读统计）与 `resetHits`（POST，清零）。

  每个词一行（拦下几条、还在用没、已删但命中过的标成「已删（历史命中）」）、命中样本表。
- 清零走确认层（清的是计数，不是词表，也不改她现在的过滤行为）。

### 12.7 B13d 收尾：承诺过的半成品，一件件落地

#### ① 日记翻页（后端早就有，页面从来没传）

`paginateDiary` 一直支持 `page`（按 7 天一页切），面板却只传 `{book, date}`——

#### ⑦ 自动发布的两道安全档位（安全闸补 2 档位）
