## 5. 三个机制（代码位点，不是推测）

1. **每个回合 ≈ 2 轮模型调用。** 当日 712 次 user 注入（461 心跳 + 251 其他）对应 1406 个 generation（1.97 倍）：
   工具环每轮都重新发送整个窗口，所以"一次开口"其实是两次全窗口计费。
2. **上下文预算今天没在管她。** 部署 `config.context = {maxTokens:500000, keepRatio:0.4, softRatio:0.85}`，
   provider spec `contextWindow:1048576, maxTokens:8192` → 宿主 `hardTokens = 1,040,384`（`Cortico-up/src/core/core.ts:324-328`）。
   实测 p50 = 615,918 **已经超过配置预算 500K**，p90/p99/max 顶在 1,048,570 ——即 **一直撞到模型上限**才停。
   两条待查的具体分支（本组今天没改行为，只标位置）：`src/core/loop.ts:1171`（"轮边界收束、批末交接"＝批内允许越界）
   与 `src/core/loop.ts:1621`（按计数检查依赖 `estimateTokens`，若估算低于真值就永远判不到超限）。
   **这是 P1 里最该动手的一块**，而且它治的正是"每次带多少"，不是"想说几次"。
3. **402 期间她在对着死端点空转，还被重试放大 4 倍。** 601 个 generation 的最大 `ordinal=3`（即 4 次尝试），
   601×4=2404 ≈ 当日失败行 2396 ——评审说的 744 次 402 与这里的量级差在统计面（见 §6）。
   失败中位 49 毫秒：几乎不花钱，但**每一拍都在撞**，且她事后读到的是"今天什么都没做"。这就是 P3。

## 7. 我对评审 B-3 的纠偏（这是负责人该说的，不是替谁辩护）

评审：「`CHECK_PROB=0.35` + 30–90 秒的投递上界约 42/小时，实测 generation 116–125/小时，是上界的 2.9 倍 → 概率门事实上没生效」。
**这个比较把两个量当成一个量了：**

- 42/小时是**投递回合**的上界估算；实测心跳投递（transcript 里以 `[system] 已安静` 开头的 user 项）
  本地 08–19 时逐小时是 **27–52 次、均值约 36**（07 时 4 次与 20 时 15 次是进程起停，不算常态），
  与"30 秒一拍 × CHECK_PROB 0.35 ≈ 42/小时"同量级。**概率门在按设计工作**，个别小时高出 42 属二项分布的正常涨落
  （120 拍 ×0.35 的标准差约 5.2，52 次是 +2σ，不构成"门没生效"）。
- 116–125/小时是**模型调用**（generation），等于「回合 × 每回合几轮」。全天 712 回合对应 1406 个 generation
  （平均 1.97 轮/回合）；停摆那段更陡——UTC 07–11 五小时内 generation 576 个，而同期心跳投递只有 190 次
  （**≥3 轮/回合**），因为 402 的重试与工具环错误轮都在往同一个回合里加调用。
  拿 116–125 去比 42 是**单位混用**：42 是回合上界，116–125 是调用数。

所以 B-3 的正确表述是：**门没问题，问题是每回合的重送与工具环轮数**——即 §5.2 的上下文硬预算与 §3 的自我重读。
把 B-3 拿去"先查概率门"会白费一轮。

另外更正我自己的历史回执：早前交付里写过「CHECK_PROB 5%→2%」，那被 `8c98859` 推翻，现值 **0.35**；
回执与代码漂了是我的问题，当场说明，不留给第三方去发现。
