# 架构图与依赖边界（一页纸看懂）

> 给"我们的东西为什么要靠宿主"这个问题一个能照着说的答案。
> 2026-11-20 起有效；数字与结论都是实测，不是设计意图。

## 一、三层，谁是谁

```
┌──────────────────────────────────────────────────────────────┐
│ ① 能力包  packages/kernel · capabilities/* · shared/*         │
│    纯业务：记忆怎么办、看图怎么办、看片规矩怎么办              │
│    零第三方依赖（只用 node:fs / node:path 这些标准库）         │
│    ★ 能脱离任何宿主独立加载——已实测                          │
└──────────────────────────────────────────────────────────────┘
                          ↑ 只吃"注入"（别人把原料递进来）
┌──────────────────────────────────────────────────────────────┐
│ ② 适配层  packages/adapters/*                                 │
│    翻译官：把宿主的形状 ↔ 我们的形状                          │
│    cortico-bot-xiaoyu / cortico-world-* / cortico-adapter      │
│    同样零依赖，只有形状声明（不 import 宿主任何文件）          │
└──────────────────────────────────────────────────────────────┘
                          ↑
┌──────────────────────────────────────────────────────────────┐
│ ③ 宿主（当前是 Cortico，可换）  host/cortico/                  │
│    跑起来的进程：模型调用、会话、定时器、HTTP 服务            │
│    拥有数据：data/media（附件）、data/runs（事件与转录）       │
└──────────────────────────────────────────────────────────────┘
```

**①②都是我们的；③不是。**

## 二、为什么有些功能必须落在 ③

| 功能 | 谁做 | 为什么 |
|---|---|---|
| 她"记得"雨声那条 | 我们 | 纯计算 + 读写自己的文件 |
| 她"刷 B 站候选池" | 我们 | 自己发 HTTP，凭据自己读 |
| 看主人发来的图 | **一半** | 图是**宿主收的**，落在宿主的盘上 |
| 调大模型 | 宿主 | 密钥、计费、重试、流式中断都在它那儿 |
| 每 5 分钟叫醒她 | 宿主 | 定时器是它的进程 |
| 网页上点按钮 | 宿主 | HTTP 服务是它起的 |

## 三、"看图"为什么算一半

```
主人 ──发图──→ 宿主接收 ──落盘──→ <部署家>/data/media/ab12cd.png
                 │                        ▲
                 │                        │ 文件在**宿主的家**里
                 └──写事件──→ <部署家>/data/runs/<run>/events.jsonl
```

图不是我们收的。我们只能"去它的盘上找那张图"。两条路：

| 走法 | 做法 | 代价 |
|---|---|---|
| **A. 问宿主要**（当前实现） | 调 `host.blob('log:ab12cd')` | 宿主改了位置我们照常能用 |
| B. 自己翻盘 | 直接读 `data/media/ab12cd.png` | 宿主换存储方式我们就坏 |

选 A 不是因为离不开，而是 **A 更稳**：B 等于硬编码别人的内部布局。

同一个道理，`world.tools()` 里"列出还有哪些图"要读事件库——`WorldHost.store` 是宿主给的读口。
宿主给 `WorldHost`（world 侧）就三样齐全；给 `CoreApi`（bot 侧）只给 `blob`。
**这不是我们被卡，是插槽的孔数不同。**

## 四、比喻

```
宿主 = 一栋公寓楼
我们 = 住在里面的装修队
```

- **墙纸 / 家具 / 灯具**（业务逻辑）：自己带，想怎么装怎么装
- **水管 / 电表 / 门禁**（模型调用、定时器、HTTP）：楼里的设施，改不了
- **快递柜**（图片与事件存储）：楼里的。可以按地址去取（A：问物业要钥匙），也可以摸黑撬（B：自己翻）

**换楼**：家具照搬，只需重新量门宽——那是 `packages/adapters/` 的活，业务代码一行不动。

## 五、实测证据

```bash
# ① 我们的代码对第三方依赖 = 0
node -e "..."   # grep 'from 非相对路径' 全仓 packages/ → 只有 node:*
# 输出：from 'node:child_process' / 'node:crypto' / 'node:fs' / ... 共 9 个标准库

# ② 六个能力包在没有任何宿主的情况下全部加载成功
node --input-type=module -e "await import('...cap-console-image/src/index.ts') ..."
# 输出：6 个能力包在**没有任何宿主**的情况下全部加载成功

# ③ 宿主恢复成纯上游后，三个扩展照样加载
# 输出：OK cortico-bot-xiaoyu | id=xiaoyu / OK cortico-world-bilibili | id=bili-account …
```

## 六、"依赖"到底是什么，一句话

> **宿主提供什么原料，决定我们能在它上面装多少功能。**

它给事件库，我们就能"列出还有哪些图"；
它只给 blob，我们就只能"按句柄看一张"。

**这不是缺陷，是物理事实**——插座有几个孔决定能插几个插头；
电器的内部电路跟插座无关。

## 七、想彻底不靠它还剩下什么

自己做宿主。那时代替 `packages/adapters/`，能力包一行不改。
要自己写：模型调用、会话管理、定时器、HTTP 服务。

**判断：现在不值得。** ③ 那层恰恰是"复用别人轮子"的地方。

## 八、当前各能力包吃什么（注入清单）

| 能力包 | 注入什么 | 来源 |
|---|---|---|
| `cap-state-rhythm` | `fieldsFile` / `lifeFile` | 部署目录路径 |
| `cap-memory` | `memoRoot` / `workspaceDir` / 取当前心情 | 部署目录路径 |
| `cap-journal` | 两本日记 / 判卡 / 意见箱路径 + git | 部署目录路径 |
| `cap-vision` | `dataDir` + ffmpeg 路径 | 部署目录路径 |
| `cap-media-studio` | 资源/输出/BGM 目录 + 渲染管线 | 部署目录路径 |
| `cap-bilibili` | `dataDir` + 凭据文件 + 看片史注入 | 部署目录 + 自身账 |
| `cap-history` | `dataDir`（只读 `runs/`） | 部署目录路径 |
| `cap-console-image` | 列图 / 取图 / 判断模型收不收图 | **宿主**（WorldHost 三样） |

只有最后一行需要宿主开口，其余全是"告诉我文件在哪"。
